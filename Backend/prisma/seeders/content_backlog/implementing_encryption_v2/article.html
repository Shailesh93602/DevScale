Implementing Encryption Correctly

Encryption is reversible by design: whoever holds the key can recover the plaintext. That makes it the right tool for data you must read back, such as third-party API keys or personal data, and the wrong tool for passwords, which should be hashed with a password-hashing function (argon2id or bcrypt) instead. Bcrypt is not an encryption library; what it produces cannot be decrypted.

1. Choose an authenticated cipher

Use AES-256-GCM (or ChaCha20-Poly1305). These are AEAD ciphers: besides hiding the data they produce an authentication tag, so a modified ciphertext fails to decrypt instead of silently yielding garbage. Avoid unauthenticated modes such as AES-CBC without a MAC, and never use ECB.

2. Never reuse an IV with the same key

Generate a new random 12-byte IV for every encryption with crypto.randomBytes(12) and store it alongside the ciphertext and tag. Reusing an IV with GCM leaks the relationship between messages and can expose the authentication key.

3. Manage keys separately

Load keys from a key-management service or secret store, not from the database or the repository. Record which key encrypted each value so keys can be rotated: decrypt with the old key, re-encrypt with the new one.

4. Encrypt in transit too

Data at rest is only half the picture. Serve every endpoint over TLS (HTTPS) and require TLS on database connections, so the plaintext is never exposed on the network.

Conclusion

Use an authenticated cipher, a fresh IV per message and keys held outside the data store, and keep password storage on a password-hashing function rather than encryption.
